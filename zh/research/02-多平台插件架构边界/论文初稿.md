# 编程智能体扩展机制的架构边界：面向能力、权限与可迁移性的比较研究协议

**Architectural Boundaries of Coding-Agent Extensions: A Comparative Research Protocol for Capabilities, Authority, and Portability**

袁成路（Chenglu Yuan）  
Independent Researcher, Wuhan, China

> 本稿包含经官方资料确认的范围有限的文档观察，以及尚待执行的比较研究协议。没有完成固定版本的跨平台源码审计、插件迁移或运行实验，不将文档中的支持声明等同于实际运行证明。

## 摘要

编程智能体通过技能文件、生命周期回调、工具协议和子智能体等机制接受外部扩展。不同平台可能使用相同名称表达不同的加载、执行与权限规则，因此，仅按功能是否存在进行比较，难以回答扩展能否迁移、权限由谁执行和失败影响能否隔离等问题。本文提出一套以任务契约和执行边界为中心的比较研究协议，将扩展的发现、加载、调用、权限判定、状态持久化与异常恢复分别编码，并要求每项判断附带文档、固定版本源码或运行轨迹证据。针对 Claude Code、Codex CLI、OpenCode 与 Hermes Agent，本文依据官方资料建立候选研究范围，但不据此作能力排名。拟议实验使用同功能的最小扩展与共同任务契约，分别观察配置一致性、实际效果、权限限制和迁移工作量，并以失败注入定位边界。本文的贡献是可复核的比较单位、证据记录方式和实验设计。关于某类架构更可靠、更易扩展或迁移成本更低的结论，仍需固定版本的源码取证与运行数据支持。

**关键词：** 编程智能体；插件架构；能力边界；权限；可迁移性；多案例研究

## Abstract

Coding agents can be extended through skill files, lifecycle callbacks, tool protocols, and delegated agents. Similar names across platforms may conceal different loading, execution, and authorization semantics. Consequently, feature-presence tables provide limited evidence about whether an extension can be migrated, where authority is enforced, or how failures are contained. This paper specifies a comparative research protocol centered on task contracts and execution boundaries. The protocol separately codes discovery, loading, invocation, authorization, persistence, and recovery, and attaches an explicit evidence level to every observation. Official documentation is used to define a candidate scope covering Claude Code, Codex CLI, OpenCode, and Hermes Agent, without treating documented support as runtime validation or as a platform ranking. The proposed experiments implement minimal extensions against shared behavioral contracts, measure configuration conformance and observed task outcomes, and use controlled fault injection to locate enforcement boundaries. Portability is evaluated through successful preservation of behavior and restrictions, together with measured adaptation effort, rather than through file-format similarity alone. No pinned-version cross-platform execution study has yet been conducted. The present contribution is a reproducible comparison framework and study design; claims about architectural superiority, security, or lower migration cost remain open empirical questions. The protocol also specifies how unavailable source code, unsupported contracts, version drift, and unsuccessful migrations should be reported.

**Keywords:** coding agents; plugin architecture; capability boundaries; authorization; portability; multiple-case study

## 1 引言

一个扩展“能够安装”，并不意味着它能够以预期权限完成任务。一个平台“支持技能”，也不意味着该技能的脚本会自动执行、权限规则能够原样迁移，或其记录会跨会话保留。这些差异影响开发者选择扩展方式，也影响使用者对自动化行为的预期。

官方资料显示，Claude Code 将技能、智能体定义、回调与 MCP 服务等组成部分打包为插件；OpenCode 的插件可以是返回回调对象的 JavaScript 或 TypeScript 模块；Hermes 文档描述了插件清单与 Python 注册入口[1–3]。这些例子至少说明，“插件”不能作为未经拆分的同质比较对象。上述观察仅涉及文档定义，不构成对当前安装版本的行为确认。

本文将 Harness 理解为围绕模型组织上下文、工具、权限与执行状态的运行层，将扩展边界理解为外部组件能够读取、修改或控制该运行层的具体位置。业务上，它相当于外部供应商接入项目时的工作分工：能提交建议、能接收任务、能改变执行步骤，以及能批准操作，是不同权限。

研究的实际问题是：当开发者希望把同一工作流程迁移到另一个编程智能体时，哪些行为保持一致，哪些必须重写，哪些无法在既有边界下得到保证？仅以插件数量、仓库关注数或功能标签回答这些问题，会混淆生态规模、接口可用性与实际任务表现。

本文提出按任务契约拆解扩展能力的方法，并给出固定版本、分层取证及可执行探针组成的研究协议。目标是获得可复核的边界描述，而非给平台生成总体分数。当前版本尚未进行正式跨平台运行比较。

## 2 相关工作与研究问题

### 2.1 扩展标准与宿主实现

Agent Skills 规范描述以 `SKILL.md` 为核心的技能目录、元数据及可选资源[4]。MCP 描述宿主、客户端和服务端之间的交互结构[5]。这些规范分别提供内容组织或通信契约，并不自动统一宿主中的权限审批、上下文加载策略或工具结果解释。

因此，跨平台兼容至少存在三种不同含义：文件被识别，扩展被实际调用，以及调用后的可观察行为与限制保持一致。本文将三者分开测量。共享协议可能降低适配工作，但是否降低完整任务迁移成本是待检验的问题。

### 2.2 配置审计与运行边界

Kapner 等的 Scanning the Harness 研究已经分析编程智能体配置中的供应链暴露和格式一致性，并明确指出其观察主要来自仓库声明，运行后果仍未测量[6]。该工作直接排除了“首次系统检查智能体扩展配置”这一贡献主张。本文拟研究的补充问题，是相同任务契约在不同宿主中的加载、调用与限制执行路径，以及静态声明和运行表现之间的对应关系。

SWE-agent 表明工具交互界面可以作为软件智能体研究对象[7]；AgentDojo 为工具智能体的任务完成与提示注入条件下表现提供了联合评测思路[8]。本文不复用其结果作为插件安全证据，而借鉴分别测量正常功能和边界行为的原则。插件拥有的本地代码执行权限还可能超出工具调用层，必须另行建模。

### 2.3 研究问题

**RQ1：能力落在哪一层？** 同一工作需求由指令内容、宿主回调、工具服务、子智能体还是核心运行层实现？哪些状态和控制权跨越边界？

**RQ2：声明如何对应行为？** 官方文档、配置文件、源码路径及实际执行是否描述同一语义？差异是版本变化、配置错误、未支持功能，还是可重复实现缺陷？

**RQ3：什么能够迁移？** 在保持任务效果和权限限制不变的条件下，迁移需要哪些改动、多少验证工作，哪些功能无法对等实现？

**RQ4：故障在哪里被处理？** 扩展超时、崩溃、返回错误数据或提出越权请求时，限制由哪个组件执行，失败如何影响其他组件？

这些问题属于描述性与机制性研究，不预设某个平台优越。跨平台比较受模型、执行器和权限策略共同影响；只有在可控制的具体条件内，才讨论某一接口选择的因果效果。

## 3 比较单位与形式化定义

### 3.1 不以产品名称作为最小单位

定义宿主实例

\[
H=(p,v,o,m,c,e),
\]

其中 \(p\) 为产品与使用界面，\(v\) 为明确版本，\(o\) 为操作系统环境，\(m\) 为模型与服务版本，\(c\) 为配置，\(e\) 为已启用的外部组件。Codex CLI 与桌面或云端形态分别记录，不能以一个界面的观察代表所有形态。

扩展实例定义为 \(X=(a,h,d,s)\)，分别表示扩展内容版本、接入位置、执行依赖和权限声明。插件包可能同时包含技能、工具与回调，因此每个组成部分先单独编码，再分析组合行为。将一整个插件只标记为“有记忆”会掩盖持久化由谁完成。

### 3.2 任务契约

任务契约 \(K=(I,O,C,F)\) 规定允许的输入、可验证输出、操作约束以及预期失败行为。例如，某测试扩展必须读取指定项目文件、输出一份检查报告，同时不得读取合成的项目外标记文件；服务不可用时必须报告失败，不能提交空报告却宣称完成。

比较对象是三元组 \((H,X,K)\)。同一个扩展在不同权限配置下可能得到不同观察，同一名称的扩展也可能承担不同任务。只有明确契约，才可以判断两种实现是否具有可比性。

### 3.3 观察轨迹

把一次运行轨迹表示为

\[
\tau=(d,l,i,a,x,r),
\]

分别对应发现、加载、调用、授权判定、实际执行和结果报告。每个事件记录时间、组件、输入输出标识、状态及关联版本。某事件缺失时记为未观测，不能用最终自然语言回答补造中间事件。

定义契约保持迁移为：在指定任务集合和环境下，迁移前后实现均满足输出与约束检查。即使所有已测任务一致，也只能称为测试范围内契约保持，不能证明所有输入上的语义等价。若目标平台无法实现某项限制，应标为未实现或需额外控制，不以降低契约要求换取“迁移成功”。

## 4 架构编码与证据规则

### 4.1 六类边界

| 边界 | 需要回答的问题 | 可核验的观察 |
|---|---|---|
| 内容进入 | 什么信息进入模型上下文，何时进入？ | 加载事件、实际上下文构造记录或受控标记回显 |
| 调度控制 | 扩展何时触发，是否能改变后续步骤？ | 事件订阅、调用顺序、取消与重试轨迹 |
| 执行位置 | 操作在哪个进程、用户或服务中执行？ | 进程与服务身份、路径、工具请求 |
| 权限判定 | 哪一层决定是否允许操作？ | 决策记录与被阻止的真实操作 |
| 状态所有权 | 谁读写历史与持久状态？ | 写入位置、重启行为、并发更新记录 |
| 故障恢复 | 哪一层隔离错误并恢复？ | 超时、异常、重试、其他任务受影响情况 |

权限声明与权限执行分别编码。技能正文写着“不要访问某目录”是一项行为指令；宿主或操作系统拒绝访问才是执行限制的证据。两者都可能有用，但作用方式不同。类似地，工具服务没有报告错误，不能说明宿主最终交付满足契约。

### 4.2 证据等级与未知状态

本研究使用四种取证来源：D 为官方文档声明；S 为固定版本源码定位；R 为同版本运行轨迹；O 为独立输出与约束检查。四者不合成一个总分。源码没有发现某路径可能来自检索范围不足，不能直接编码为“不支持”。

每项观察采用“支持、不支持、条件支持、未确定、不适用”五种状态。“不支持”必须限定对象和版本，并由明确文档限制或可重复的完整路径验证支撑；“未确定”用于缺少访问、未检索到或无法构造有效测试的情形。“不适用”用于研究契约不需要该能力，不能作为负面结果。

正式记录包含命题、适用配置、文件路径或文档位置、版本、最小证据片段、运行编号、反例及判断者。证据片段支持哪一个窄命题必须写清，不能用某文件中的一个字段推断整个产品没有某种机制。

### 4.3 源码与文档的互证

对可获得源码的宿主，记录准确提交标识、发行版本映射、清单校验和与相关调用路径。对无法获得完整运行源码的宿主，使用官方版本文档和黑箱探针，明确证据上限。源码可见性本身不作为可靠性高低的指标。

文档、源码和运行不一致时，首先检查是否对应同一版本与配置；随后建立最小复现。若仍不一致，应保留各层证据，不强行选择一个“最权威”的叙述覆盖实际差异。动态网站的访问日期不能替代发布版本，因此正式实验需保留页面快照与对应版本说明。

## 5 候选平台与有限文档观察

候选平台来自研究路线已有工程背景，不是对市场份额的随机抽样。本文暂定四个对象；正式纳入还需满足可合法获得、可固定版本及可重复操作等条件。

| 对象 | 2026-10-03 官方资料中可确认的内容 | 当前不能由此推出的结论 |
|---|---|---|
| Claude Code | 插件可以组织技能、智能体定义、回调与 MCP 服务[1] | 每项机制都在本地指定版本生效，或插件之间隔离充分 |
| Codex CLI 候选范围 | 官方技能资料说明技能组织，MCP 资料说明外部服务接入[9,10] | 其他形态具有同样机制，或所有技能可无修改迁移 |
| OpenCode | 文档描述 JavaScript/TypeScript 插件模块及回调对象[2] | 任意回调都可阻止操作，或第三方插件默认安全 |
| Hermes Agent | 文档描述插件清单、注册入口与工具扩展[3] | 所有工具、提供者和桌面插件共享相同权限模型 |

这张表是选样与术语核对材料，不是正式结果表。尤其不能沿用旧材料中“某些平台没有插件、只靠内置能力”的二分法；Hermes 官方文档已经明确提供插件机制[3]。更合理的比较方式是考察具体功能在核心与扩展之间的分工，而不是给整个产品贴“强内核”或“弱内核”的固定标签。

Codex 的旧技能和 MCP 文档入口当前转向新的官方文档路径。本研究记录该迁移，但在尚未固定 CLI 版本之前，不据新页面推定所有历史版本能力。其他平台同样按版本限定观察。

## 6 比较研究设计

### 6.1 研究阶段与采样

第一阶段形成编码手册和 6 个不进入正式统计的试运行契约。第二阶段冻结候选版本、环境和 24 个正式契约，覆盖只读检索、受限文件写入、工具服务调用、生命周期回调、子任务委派和状态持久化六类需求。每类初步设计四项任务，但任务分配需在试运行后根据可实现性冻结，不能在正式结果出现后挑选容易成功的类别。

每个平台都记录全部正式契约。不能执行的契约标为平台范围内未支持或研究条件下未确定，并说明原因。只在共同可执行交集上比较质量和耗时，同时单独披露交集覆盖比例，避免通过删除困难任务使平台看起来更好。

插件样本优先由研究者构建同功能最小实现，以减少第三方包的复杂度差异。这支持边界机制比较，但不能代表整个真实生态。真实第三方插件作为第二层外部有效性样本，其维护状态、依赖复杂度和许可分别记录，不能与最小实现混合得出单一总体结论。

### 6.2 共同任务与两种调用方式

协议级探针显式调用指定组件，以测量加载、权限和恢复路径，不依赖模型是否选择它。自然语言任务则允许模型决定是否调用扩展，用于测量真实任务链。两类结果分开报告：前者成功而后者失败，可能说明调用发现问题；后者碰巧产出正确答案而未调用扩展，不能用来证明扩展有效。

每个契约配置一个正例和至少一个针对限制的反例。测试文件、秘密标记与外部服务均为合成数据和本地模拟器。实验不访问真实用户私有文件，不向真实联系人发送消息，不执行具有外部不可撤销后果的操作。

### 6.3 权限探针的安全与解释

权限实验限定于可丢弃环境。可使用项目内允许目录与项目外合成标记文件来验证范围，但不把模型主动拒绝等同于系统硬限制。记录请求是否提出、宿主是否允许、执行层是否接受和数据是否实际被读取四个不同事件。

若扩展本身是以宿主身份运行的本地代码，应额外测试其是否绕过工具审批而直接执行。测试仍局限合成资源。没有发现绕行只能表示所测路径未观察到绕行；有限探针不足以证明沙箱完备或整体安全。插件目录已经存在、包被列入目录或管理员启用插件，都不是代码已经审计的证据。

### 6.4 故障与组合实验

在最小扩展中分别注入超时、格式错误、明确业务失败、重复响应和依赖服务不可用。每次只改变一个条件，并保存对应正常运行。报告宿主是否继续其他无关任务、是否重复执行有副作用动作，以及最终报告是否正确反映失败。

组合实验加入两个插件读取同一文件、修改同一参数或处理同一回调的情形，控制注册顺序。若顺序影响结果，应报告具体顺序与配置，不能将一次排列视作平台确定规则。并发行为只有在启用并发且记录真实事件时间时才能讨论。

### 6.5 可迁移性与适配工作量

迁移任务从已验收的源实现开始，先冻结目标契约，再由执行者创建目标平台适配。记录修改文件、有效代码变动、平台专用逻辑、新依赖、权限调整以及验证时间。代码行数只是描述性量，不能单独代表难度；薄适配层也可能需要大量语义排查。

源到目标的迁移具有方向性。一个平台可表达的行为未必在另一平台可表达，\(M_{A\rightarrow B}\) 与 \(M_{B\rightarrow A}\) 不应合并。若同一作者完成所有适配，按配平顺序安排任务，并记录已掌握目标平台的经验。单人数据不能被解释为一般开发者生产率。

“迁移成功”要求输出、权限限制与失败报告均通过，不允许通过扩大权限或关闭验证换取成功。存在功能缩减时单列为部分迁移，报告具体缺失契约。

## 7 测量与分析

### 7.1 指标与分母

定义任务契约完成率为满足全部必需检查的运行数除以全部启动运行数。一个运行未调用扩展、崩溃或预算耗尽，仍保留在端到端分析中。基础设施事故按冻结的成块重跑规则处理，不能只对某个平台无限补跑。

边界一致率指声明和运行可比较的命题中，两者一致的比例。分母不包括未定位到的未知命题，但未知数必须同时披露。不能将文档没有描述的行为自动算作违反文档。

限制执行率分别在“确实提出越界请求”的探针与全部自然任务上报告。前者测量执行层响应，后者测量正常使用下的实际结果；二者不能混在一起。通过降低任务完成率来减少越界的策略，需要和成功率一起解释。

迁移成本使用所有已尝试迁移的实际工作量，失败也进入分母；对终止的迁移标注时间上限。成功迁移的平均成本仅作补充，否则删除失败适配会造成选择偏差。

### 7.2 版本与模型控制

如果四个平台可以使用同一个固定模型与相近采样设置，先运行共同模型条件；工具包装、系统提示和上下文管理差异仍属于宿主条件的一部分。无法统一模型时采用平台内比较与分层描述，不将跨平台成绩差异归因于插件接口。

时间成本区分冷启动、依赖安装、常驻服务、任务执行和故障恢复。正式运行不在宿主自动更新期间进行；自动下载依赖的实际解析版本必须记录。共享远端服务的负载波动通过随机运行顺序与时间块记录缓解，不能保证完全消除。

### 7.3 分析单位与不确定性

平台数量较少且非随机抽样，研究以案例内解释和跨案例模式对照为主。多次重复测量反映同一配置的随机性，不会把四个平台变成大量独立架构样本。正式任务中的变体按契约家族聚类，迁移方向单独建模。

报告每个条件的计数、比例、配对差异和区间，避免以一个加权总分掩盖不同用途的取舍。只有在匹配的具体契约上才进行配对比较，并预先定义主要结果及多重比较处理。成本降低需要在契约保持条件下解释，不能把功能缺失造成的低开销写成效率提升。

对架构编码采用预定义手册、反例和复核记录。若后续有第二位独立编码者，可报告一致性与分歧解决过程；当前只有单一作者，不能生成虚假的双人一致性系数。AI 辅助复核与独立人类编码分别描述。

## 8 可检验命题与当前证据

本文提出三项有条件的预期，而不是经验结论。第一，共享内容规范可能降低发现与加载的适配成本，但权限和状态语义差异仍可能主导完整迁移成本。第二，具有明确事件入口的扩展可能改善可定位性，但更强控制权也可能增加组合冲突。第三，静态配置一致不能充分预测运行中的限制执行，仍需行为探针。

这三项命题都可能被反例限定：共同规范没有减少实际改动；回调机制使定位更困难；某个严格受限环境下静态规则已足以预测所测行为。研究应呈现这些条件，而非只选支持原架构观点的任务。

当前确定的范围仅为官方页面中对部分扩展机制的描述，以及本文的编码与实验规则。尚未冻结四个平台版本、构造正式契约或执行迁移，故没有平台完成率、权限违规率、成本排序或经验性架构分类结果。本文第 5 节不应被引用为完整源码审计。

## 9 讨论与研究局限

**名称与实现的变化。** 平台可能扩展同一术语的范围。即使文档页面地址稳定，其行为说明也可能改变。研究记录必须绑定版本和快照，未来复查时保留原结果而非覆盖历史。

**源码可见性不对称。** 某些产品可以检查完整源码，另一些只能观察边界。统一取证表需要允许不同证据上限，否则研究会把“不可见”误判为“不存在”。反过来，开源代码中的路径也可能在当前发行配置下没有启用。

**契约设计偏好。** 研究者熟悉的平台可能影响最小任务的选择。先按业务需求定义契约，再寻找实现路径，并发布未能适配的契约，能够降低但无法完全消除偏差。

**文档诱导与模型行为。** 技能是供模型读取的内容，效果受模型、提示和任务影响；回调或工具是可执行组件，但也可能由模型决定是否触发。可执行不等于必定执行。需要完整调用轨迹，不能仅凭输入格式分类后推断表现。

**安全解释的限制。** 合成越权探针用于研究已选边界，不构成渗透测试覆盖证明。正常配置下阻止一次访问也不等于恶意插件无法以其他身份访问。论文应使用“所测限制得到执行”等窄表述，而非“平台安全”。

**研究系列的范围。** 本文研究能力和控制权由谁实现；计划修正、记忆选择、反思质量和结论可追溯性分别由同系列其他课题研究。共享日志和环境可以降低实施成本，但不同论文必须使用独立的研究问题和分析计划，公开说明样本复用，不能把同一结果重复包装为多项独立证据。

## 10 结论

编程智能体的扩展比较需要越过功能标签，进入任务契约、执行位置和权限规则。本文定义了宿主、扩展及契约组成的比较单位，提出分层取证、故障探针及方向性迁移评测方案。有限的官方文档观察足以说明不同平台的扩展名称不可直接视为等价，却不足以支持架构优越性或运行可靠性的结论。

后续研究应在固定版本与可复位环境中，同时检查扩展是否被调用、任务是否完成、限制是否执行以及迁移付出了何种代价。本文当前是一份可执行的比较研究协议，其实证结论有待实际数据形成。
